Testing an application

A page's whole contract lives on the server: the view's bindings and rules, its filters, the route's authorization, the controller's commands. NE.Standard.UI.Testing checks that contract where it lives. A test boots the application's own startup with no platform under it, opens a page through the host's real path, acts on its components the way a reader does and reads what the page received — no browser, no web host.

dotnet add package NE.Standard.UI.Testing

The package depends on the engine alone and on no test framework or assertion library: a page answers with plain values, and a misuse — a component that is not there, a press on a button a reader could not press — throws InvalidOperationException. The examples below use xUnit.

A first test

public sealed class SignUpScreenTests
{
    [Fact]
    public async Task AnInvalidEmailShowsTheRuleAndTheSubmitIsRefused()
    {
        await using UITestApp app = UITestApp.Create<AppStartup>();
        UITestPage page = await app.OpenAsync("/screens/sign-up");
        UITestComponent email = page.ComponentBoundTo(nameof(SignUpController.Email));

        await email.SetValueAsync("not-an-email");
        UITestCommandResult submit = await page.ComponentNamed("Create account").ClickAsync();

        Assert.Equal("That does not look like an email address.", email.ValidationMessage);
        Assert.False(submit.Sent);
    }
}

The email's rule runs in the browser, so no command reaches the server and a controller-only test would never see it. Here the page evaluates the field's rules as the client does, and the submit is refused while its form has a field in error, as the browser refuses it.

The application

UITestApp.Create<TStartup>() builds the application from its UIStartupBase the way its host does — the routes, the services, every view compiled — and puts a test client where the platform would be: what the runtimes push, the dialogs they open and the files they send reach the page they are addressed to. Two optional arguments shape it:

await using UITestApp app = UITestApp.Create<AppStartup>(
    configureServices: services => services.AddSingleton<IClock>(new FixedClock(Today)),
    configureApplication: application => application.ConfigureSessions(sessions => sessions.IdleTimeout = TimeSpan.FromMinutes(5))
);

configureServices runs after the startup's own registrations, so a fake registered there replaces the real service.

The scheduler is parked. A Batch runtime answers a command with what it changed for the page that asked and keeps the rest — a posted action's writes, OnAttachedAsync's, what another page's command changed — for the scheduled flush. In a test nothing flushes on its own: page.FlushAsync() delivers it to every page attached, so what a command answered and what waits for the flush are told apart without timing.

Opening a page

app.OpenAsync(address, session) resolves the address as a page load does — the view filters, the route's authorization, a refusal sent to sign in or to the forbidden page — attaches a runtime and starts the page from the snapshot a connecting page is sent. page.Route is the route that answered:

UITestPage refused = await app.OpenAsync("/screens/admin");

Assert.Equal("/screens/sign-in", refused.Route);
Assert.Equal("/screens/sign-in?returnUrl=%2Fscreens%2Fadmin", refused.Address);

UITestPage admin = await app.OpenAsync("/screens/admin", session => session.SignIn("robin", roles: ["admin"]));

Assert.Equal("/screens/admin", admin.Route);

The session is described, then stored in the application's own session store and presented as a browser presents its cookie, so the resolver, the authorization and the filters read it as they read a real one: SignIn(userId, roles, permissions), InLanguage("ru"), InTimeZone("Europe/Berlin"). Under claims as the identity source the same user travels as the host's principal. Without a description a page opens as an anonymous first visit. page.OpenAsync(address) opens another page in the same session — following a NavigateEffect, or a second tab.

An address may carry a query, read as the route's parameters: app.OpenAsync("/screens/catalogue?role=db").

Finding a component

Call Finds
page.Component(id) the component with that id in the view
page.ComponentBoundTo(path) the one component whose value — else another property — is bound to the controller path
page.ComponentNamed(name) the one component a reader knows by that name: its title, accessible name or tooltip, as written or as shown
component.Rows, component.Row(key) a list's rows, in the order the server sent them
row.Component(id), row.ComponentBoundTo("Text") a component in the row; a path is the item's
row.ContextMenu, component.ContextMenu what a right click shows

Several components matching is an error that names them: find one by its id instead.

Reading what it shows

A component's state is read off the change sets the page received, applied the way the client applies them: Value, Title, Get(property) and Text(property) (the words in the page's language), IsVisible and IsEnabled (an ancestor collapsed, disabled or loading counts, and so does a dialog that is not open), and ValidationMessage — the strongest of the field's failing rules once the reader has been in it, the controller's bound message and the server's refusal. A row's binding is read off the row's item. The interactions the view declares run as in the browser: a part shown while a switch is on appears when the switch is written.

The page keeps the rest of what it received: page.Effects and page.EffectsOf<ShowNotificationEffect>(), the dialogs those effects opened (page.IsDialogOpen(key)), the address an address effect wrote (page.Address), the files sent to it (page.Downloads), and page.Words(value) for an effect's words. page.Controller<T>() is the controller, for what the screen does not show.

Acting on it

Every act goes through the host's own entry points — those the web hub calls — so the value gates and bounds, the command filters and authorization, the exclusive lock all run:

  • SetValueAsync(value) types into a field and leaves it: its change rules and the interactions reading it run, the value is written to the server (or held for its form under an OnSubmit binding), then its change command, then its blur rules.
  • ClickAsync() presses a component. A button that submits a form runs the form's submit rules first and is refused while a field is in error.
  • DispatchAsync(eventName, eventKeys) raises any event the component declares; eventKeys are the keys the event itself names after its row's, such as a moved row's place.
  • row.ClickAsync() presses a row; row.ChooseAsync() writes the list's chosen key where it binds one, then presses.
  • page.PressNotificationActionAsync(toast) presses a toast's action through the command path, once.

Each answers with a UITestCommandResult: Sent (whether a command reached the server), Succeeded, Error, and the Effects the page received while it ran. A row deleted with an undo, end to end:

UITestPage chat = await app.OpenAsync("/screens/chat");
UITestComponent conversation = chat.Component(ChatController.ConversationId);
UITestRow last = conversation.Rows[^1];

UITestCommandResult delete = await last.ContextMenu.Row("delete").ClickAsync();
ShowNotificationEffect toast = Assert.Single(delete.Effects.OfType<ShowNotificationEffect>());

Assert.DoesNotContain(conversation.Rows, row => row.Key == last.Key);
Assert.Equal("Undo", chat.Words(toast.Action?.Label));

await chat.PressNotificationActionAsync(toast);

Assert.Equal(last.Key, conversation.Rows[^1].Key);

What it does not model

Layout and styling; a responsive value at any width but the widest; a plain list's own filter and sort rules; item windows read as a list scrolls; popups other than dialogs — a context menu and a flyout stand open; a validation message sent into another component; the trimming and debouncing a field does in the browser; fields in a list's rows on a submit; what the web hub adds of its own, its call budget and a large value staged beside it. A row's item is the server's own object, so a property the server changed shows on it before a Batch runtime's flush sends the change. Focus, the keyboard and the DOM are the browser's: a test of those drives a browser.
