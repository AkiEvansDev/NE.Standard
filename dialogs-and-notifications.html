Dialogs and notifications

A dialog is declared by the view and rendered closed by the shell; the controller opens and closes it by key — from a command, never from an interaction alone. Notifications are a client effect with nowhere of their own on the tree — they stack up in a corner the view chooses. This page is also where a failed command's report and the error page are configured.

Declaring a dialog

Override CreateDialogs() on the view and return a list of UIDialog:

protected override IReadOnlyList<UIDialog> CreateDialogs()
    => [
        new UIDialog
        {
            Key = ReleasesController.ConfirmKey,
            CloseOnBackdrop = false,
            CloseOnEscape = false,
            Content = new StackPanelComponent()
                .SetSpacing(12)
                .AddChild(new TextComponent()
                    .SetTitle("Delete this release?")
                    .SetTitleType(UITextAppearance.Title)
                    .BindDescription(nameof(ReleasesController.Question))
                )
                .AddChild(new StackPanelComponent()
                    .SetOrientation(UIOrientation.Horizontal)
                    .SetSpacing(8)
                    .SetHorizontalAlignment(UIAlignment.End)
                    .AddChild(new ButtonComponent()
                        .SetTitle("Cancel")
                        .SetType(UIButtonType.Ghost)
                        .OnClick(nameof(ReleasesController.KeepRelease))
                    )
                    .AddChild(new ButtonComponent()
                        .SetTitle("Delete")
                        .SetType(UIButtonType.Danger)
                        .OnClick(nameof(ReleasesController.DeleteRelease))
                    )
                )
        }
    ];

The content is an ordinary component tree, bound against the view's controller like the rest of the page — here a line the controller writes before it opens the dialog, and two buttons that each run a command.

UIDialog:

Member Meaning
Key stable string a command or interaction opens/closes it by
Content the root component of the dialog's body
Surface (UISurfaceStyle) what the panel is made of — Background, Raised (default), Tinted
Placement (UIDialogPlacement) Center (default), or a full-length sheet against Left, Right, Top, Bottom — a shortcut over the members below
Width, MinWidth, MaxWidth, Height, MinHeight, MaxHeight (UIResponsive<UILayoutLength>) the panel's size on the overlay, per tier; unset, a centred panel is sized to its content under a 560 px cap, and on a phone it is the screen less a thin margin
HorizontalAlignment, VerticalAlignment (UIAlignment) where the panel stands on the overlay — Start, Center, End, Stretch; unset, the placement decides
Margin (UIResponsive<UIThickness>) the room kept between the panel and the overlay's edges, per tier
Modal whether it blocks interaction with the view underneath (default true)
CloseOnBackdrop whether clicking the backdrop closes it (default true)
CloseOnEscape whether Escape closes it (default true)
OnClose(command, arguments) a method, not an init member: the command run when the viewer dismisses the dialog by Escape or the backdrop; a close the server asks for raises nothing

The panel is placed on the overlay the way a component is placed in its host, with the same words: a 640 px editor is Width = UILayoutLength.Absolute(640), a panel pinned to the top-right corner is HorizontalAlignment = End, VerticalAlignment = Start, and a value per tier is UIResponsive<UILayoutLength>.Create(...). A sheet is the same thing spelled short: Placement = Left is a panel at the start edge, stretched top to bottom, 420 px wide unless a Width says otherwise.

A destructive confirmation turns both CloseOnBackdrop and CloseOnEscape off, so only its own buttons answer it. A non-modal sheet (Modal = false) at an edge, drawn on Surface = Background, is the shape a filter drawer or a side panel takes — the page keeps working beside it.

Opening and closing

From a controller, Context.Dialogs (IUIDialogService):

_ = await Context.Dialogs.ShowAsync(Context.Handle, ProgressKey, cancellationToken).ConfigureAwait(false);
// ... work ...
_ = await Context.Dialogs.HideAsync(Context.Handle, ProgressKey, cancellationToken).ConfigureAwait(false);

ShowAsync/HideAsync push straight to the connection, so the dialog stands open for exactly as long as the command takes — the pattern for a wait dialog nothing on its own body dismisses.

A command can instead return the effect, which is the more common shape when opening or closing is the whole of what the command does, or the last thing. The controller behind the confirmation above:

internal sealed partial class ReleasesController : UIControllerBase
{
    public const string ConfirmKey = "confirm-delete";

    private readonly List<int> _releases = [479, 480, 481];

    [RecursiveMember]
    public partial string Question { get; set; } = string.Empty;

    [UICommand]
    public UICommandResult AskBeforeDelete()
    {
        if (_releases.Count == 0)
            return UICommandResult.Ok([new ShowNotificationEffect("Nothing left to delete.", UIColorStyle.Info)]);

        Question = $"Release #{_releases[^1]} goes for good.";

        return UICommandResult.Ok([new OpenDialogEffect(ConfirmKey)]);
    }

    [UICommand]
    public UICommandResult DeleteRelease()
    {
        _releases.RemoveAt(_releases.Count - 1);

        return UICommandResult.Ok([new CloseDialogEffect(ConfirmKey), new ShowNotificationEffect("The release is gone.", UIColorStyle.Success)]);
    }

    [UICommand]
    public static UICommandResult KeepRelease()
        => UICommandResult.Ok([new CloseDialogEffect(ConfirmKey)]);
}

Changes go first, then effects, so the dialog opens on the question the command has just written.

OpenDialogEffect(dialogKey) and CloseDialogEffect(dialogKey) both take just the key. Neither can be raised by an interaction: a view that hands one to InteractOn fails to compile, so even a dialog that only opens takes a command that returns the effect.

Notifications

ShowNotificationEffect(string message, UIColorStyle severity = UIColorStyle.Info) raises a toast:

return UICommandResult.Ok([new ShowNotificationEffect("Build #481 published.", UIColorStyle.Success)]);

Severity is a UIColorStyle, and six of its members give the toast an accent in their colour: Info, Success, Warning, Danger, Primary and Accent; any other member leaves it with the plain border. A Danger toast is announced to a screen reader at once (role="alert"), every other one politely. Where a view's notifications stack is UIViewOptions.NotificationPlacement (UINotificationPlacement: Bottom — the default — or Top), set once for the view rather than per notification.

A toast carries a close button and dismisses itself after five seconds. The pointer resting on it holds it; when the pointer leaves, it gets the full five seconds again. The time is the client's own and not an option on the effect.

When a command fails

The client never reads a raw success/failure flag — both the invoke return and the push channel only apply changes and effects. So a failed command whose result carries no effects of its own — one that returned UICommandResult.Fail(error), threw, or was refused by an authorization check — gets one attached automatically: a Danger ShowNotificationEffect whose text comes from UIErrorHandlingOptions, configured through ConfigureErrorHandling:

builder.ConfigureErrorHandling(errors =>
{
    errors.NotifyOnCommandFailure = true;
    errors.IncludeExceptionDetail = false;
    errors.CommandRefusedMessage = "You are not allowed to do that.";
    errors.CommandFailedMessage = "Something went wrong. Please try again.";
    errors.ErrorPageMessage = "This page could not be shown.";
    errors.ErrorRoute = "/error";
    errors.NotFoundRoute = "/not-found";
});
Option Meaning
NotifyOnCommandFailure whether a failed command with no effects of its own is reported at all (default true)
IncludeExceptionDetail whether the real exception message reaches the browser, in the toast and on the error page — off by default, since an exception routinely carries a connection string, a table name or a file path
CommandRefusedMessage shown when a command throws an UnauthorizedAccessException — an authorization check's refusal
CommandFailedMessage shown when a command throws anything else, unless IncludeExceptionDetail is on
ErrorPageMessage what the error page's message parameter carries when IncludeExceptionDetail is off
ErrorRoute where a page goes when resolving its view throws, or rendering it does; a failing command is reported in place, never routed here
NotFoundRoute where a request for an unregistered route goes, with the requested route in its route parameter

The toast's text has three levels:

  1. What the command wrote. UICommandResult.Fail(error) is shown with its own error as it stands; a failure with no text shows nothing.
  2. A refusal. A command that throws an UnauthorizedAccessException shows CommandRefusedMessage.
  3. Anything else thrown. CommandFailedMessage, or the exception's own message when IncludeExceptionDetail is on.

Returning your own effects from a failing command is how it takes over the reporting — the automatic notification only fires when a command's result carries none. The text at every level goes through the translator, a command's own error included, and so does ErrorPageMessage — an application overrides the framework's wording by localization rather than by re-implementing the mechanism.

When a page fails

A page whose view cannot be resolved goes to ErrorRoute, and so does a page that throws while it is being rendered — a getter that fails as this reader's values are drawn — rather than answering with a bare 500. The error page receives a message navigation parameter: the exception's text when IncludeExceptionDetail is on, ErrorPageMessage otherwise. Both routes are used only when they are registered, and the error route never redirects to itself, so a failing error page cannot loop. A refusal while resolving is not an error: it goes to the sign-in or forbidden route instead (see security).
